# Arkham — Project Context for Claude

## Game vision (summary)
Arkham is an isometric, turn-based co-op PVE quest game inspired by the *Arkham Horror* board game. Setting: mid-19th century England, Lovecraftian horrors emerging. Players are detectives investigating clues across a town (districts → streets → bridges) to stop a doomsday before the clock runs out. Each player turn is followed by a "game turn" that advances enemies and the plot.

Full design lives in [GAME_DESIGN_DOCUMENT.MD](GAME_DESIGN_DOCUMENT.MD). When making design-affecting decisions, re-read it.

### Core pillars
- **Turn-based**: discrete player turn → enemy/world turn. No real-time mechanics.
- **Doomsday clock**: every turn pushes the world toward a bad ending; clue investigation pushes back.
- **Tile-based map**: districts composed of street tiles, connected by bridge tiles. Movement is street→street or street→bridge.
- **Event-driven streets**: each street can spawn events (clues, void/spawn zones, etc.).
- **Co-op**: multiple detective characters; camera follows the active player.

## About the developer
The user is a **beginner Unity developer** building this solo. They want guidance on **how to structure the game**, not just code snippets. Implications for how to assist:
- Explain *why* a structure/pattern is chosen, not only *what* to type.
- Prefer simple, idiomatic Unity patterns (MonoBehaviour + ScriptableObject) over advanced architectures (ECS, DI frameworks, custom event buses) unless there's a clear reason.
- When introducing a new concept (e.g. coroutines, ScriptableObjects, state machines), give a one-line "what it is / why we use it here" before the code.
- Break large features into small, testable steps the user can run in the editor between each step.
- Call out Editor setup the user must do manually (assigning references in inspector, creating prefabs, layers, tags) — don't assume they'll infer it from code alone.
- Avoid premature abstractions. Three near-duplicate scripts is fine early; refactor when the pattern is obvious.

**Importing 3D models into this URP project (procedure that worked for the creeps):** Asset Store models usually ship with **built-in Standard-shader materials**, which render **magenta** in URP. Fix first via **Window → Rendering → Render Pipeline Converter → Built-in to URP → Material Upgrade** (safe to run project-wide; it skips already-URP materials). Then swap the visual on the prefab using the **root-keeps-gameplay / model-as-child** pattern: the prefab root keeps its `Is Trigger` collider + gameplay scripts (`Enemy` subclass + `TileMover`), the imported model goes in as a **child**, and the placeholder's `MeshFilter` + `MeshRenderer` are removed from the root. Fit the child so it matches the collider: **height ≈ 2 units, centered on X/Z, feet at local y = −1** (the enemy root is placed 1 unit above the tile via `Enemy.WorldYOffset`, and the old capsule's bottom sat on the tile — so local y = −1 puts the model's feet on the tile). Compute the fit from the model's measured renderer bounds: `scale = 2 / boundsHeight`, `pos = (−scale·center.x, −1 − scale·min.y, −scale·center.z)`. Never scale the **root** (it drives gameplay positioning) — only the child.

## Current architecture conventions
Patterns the existing code follows. Honor these when extending; deviate only with a clear reason.

- **`TurnManager` is the event hub** ([Assets/Scripts/Core/TurnManager.cs](Assets/Scripts/Core/TurnManager.cs)). State lives in the `GameState` enum (`PlayerTurn`, `WorldTurn`, `Combat`, `GameOver`, `Victory`). Systems subscribe to its events (`OnPlayerTurnStart`, `OnWorldTurnStart`, `OnGameOver`, `OnVictory`, `OnCombatLog`, `OnCombatStart(Player, Enemy)`, `OnCombatEnd`) rather than polling state. Always pair `+=` in `OnEnable` with `-=` in `OnDisable`.
- **Lose/win triggers go through `TurnManager`** — call `TriggerGameOver()` (guarded against double-fire; if called while in `Combat` it also fires `OnCombatEnd` so combat UI cleans up before `OnGameOver`) or let `ClueTracker.OnAllCluesFound` / `DoomsdayClock.OnDoomsdayReached` flow through it.
- **World turn is a coroutine** ([Assets/Scripts/Core/TurnManager.cs](Assets/Scripts/Core/TurnManager.cs) `RunWorldTurn`). It fires `OnWorldTurnStart` for UI listeners, then iterates enemies one at a time calling `enemy.RunWorldTurn()`. If an enemy triggers combat (state becomes `Combat`), the coroutine `yield`s until combat exits, then continues with the remaining enemies. Doom only advances after all enemies have acted. Enemies do **not** subscribe to `OnWorldTurnStart` — the manager drives them directly.
- **Combat flow** — entering combat goes through `TurnManager.EnterCombat(player, enemy)` (allowed from `PlayerTurn` or `WorldTurn`); exiting goes through `ExitCombat()` and restores whichever state preceded the fight (so a world-turn fight resumes the world turn). [CombatController.cs](Assets/Scripts/Core/CombatController.cs) owns the round logic and exposes two player actions, each of which spends the round and is followed by an enemy counter (`EnemyCounter`): **`Attack()`** rolls Strength to hit (deals `attackDamage`) but leaves you open, so the counter always lands; **`Defend()`** forgoes your attack and rolls Agility to block that counter. All skill checks go through [CombatResolver.cs](Assets/Scripts/Core/CombatResolver.cs): a **d10**, success when `roll <= stat` (Strength for Attack, Agility for Defend) — so a `0..10` stat is a `stat×10%` chance. The only way to avoid incoming damage is to Defend, which makes enemy `attackDamage` / player `maxHealth` the key balance knobs. [CombatPanel.cs](Assets/Scripts/UI/CombatPanel.cs) is the UI listener: subscribes to `OnCombatStart`/`OnCombatEnd`, shows/hides the panel root, binds the Attack button to `CombatController.Attack()` and the Defend button to `CombatController.Defend()`. **The `CombatPanel` script must live on a GameObject that stays active** (the `CombatPanelController` sibling under Canvas) — never on the panel root it toggles, or it deactivates itself and stops listening.
- **Prefab-instantiated objects use an `Init(...)` method** for scene references. Prefab assets cannot hold scene-object references on serialized fields — see [Enemy.cs](Assets/Scripts/Entities/Enemy.cs) / [EnemySpawner.cs](Assets/Scripts/Entities/EnemySpawner.cs). Clue prefabs don't need wiring (no scene refs); the player handles collection.
- **Script execution order**: only [Player.cs](Assets/Scripts/Player/Player.cs) has `[DefaultExecutionOrder(-100)]` so its `Start` runs before spawners (`ClueSpawner`, `EnemySpawner`) that read `player.CurrentTile`. Don't add execution-order attributes elsewhere without a concrete ordering problem.
- **Namespaces follow folder layout**: `Arkham.Core`, `Arkham.Map`, `Arkham.Players`, `Arkham.Events`, `Arkham.Entities`, `Arkham.UI`. New scripts go in the matching folder + namespace.
- **Visual prefabs that sit on tiles** (Clue sphere, enemy creep models on a capsule collider) use `Is Trigger` colliders so they don't physically block the player/enemies. Note: `Physics.Raycast` still hits trigger colliders by default (`queriesHitTriggers = true`), so clicks on an occupant prefab do NOT fall through to the tile beneath. [PlayerInputController.cs](Assets/Scripts/Player/PlayerInputController.cs) handles this by resolving an Enemy-hit back to `enemy.CurrentTile`. Repeat that resolver pattern for any new clickable tile-occupant.
- **Map is a graph wired from hand-placed Tiles** ([Assets/Scripts/Map/MapGraph.cs](Assets/Scripts/Map/MapGraph.cs)). The visuals (sprites, district grounds, bridges) live as plain GameObjects in the scene that you author by hand — `MapGraph` does **not** instantiate any visuals. It just reads positions off Tile references and builds the data graph. Nodes are `MapNode` data objects (id, `NodeType.Street`/`Bridge`, districtId, world pos, neighbours, `NodeState.Clean`/`HasClue`/`Void`). [Tile.cs](Assets/Scripts/Map/Tile.cs) is the click/highlight component bound to a `MapNode` via `tile.Bind(node)` at Awake. **Highlight:** `Tile.SetHighlight` brightens the tile's child `SpriteRenderer` (sets its `color` to `HighlightTint`, an >1 multiply that lights up the dark art) if present; otherwise it falls back to tinting a child `Renderer`'s material yellow (placeholder-cube behaviour). Each art tile owns its sprite as a child (`Wedge` for streets, `Sprite` for bridges), so the highlight lights up the actual street/bridge art. Slot convention: in district `d`, street index `d` is the outward street (faces away from the triangle); the other two indices are rim streets each owning one bridge; the bridge between districts `a` and `b` uses `a`'s street index `b` and `b`'s street index `a`. All 3 streets in a district are mutually connected; a bridge connects only to its 2 designated rim streets. Districts themselves are pure ground visuals, **not** nodes. Movement and pathfinding (Enemy step-toward-player, EnemySpawner min-distance) use BFS over `MapNode.Neighbours` — never duplicate that math.
- **Enemy lookup** uses `Object.FindObjectsByType<Enemy>(FindObjectsSortMode.None)` (Unity 6 API). Fine for tiny grids; revisit if enemy counts get large.
- **Enemy animation is driven off `TileMover.IsMoving`, not gameplay events** ([EnemyAnimator.cs](Assets/Scripts/Entities/EnemyAnimator.cs)). The three enemy creep models share one tiny `AnimatorController` ([Assets/Art/Enemies/CreepAnimator.controller](Assets/Art/Enemies/CreepAnimator.controller)): two states **Idle** (default) ⇄ **Walk**, driven by a single `Moving` **bool**. `EnemyAnimator` lives on the enemy root (next to `TileMover`) and each frame sets `Moving = TileMover.IsMoving` — so the creep walks during the 0.25s tile slide and idles when stopped. ⚠️ **The creep model is a `LODGroup` with TWO Animators** (`Creep_mesh` LOD0 + `Creep_mesh_lod1` LOD1) — `EnemyAnimator` uses `GetComponentsInChildren<Animator>` (plural) and drives **all** of them, and **both** LOD Animators must have `CreepAnimator` assigned. (Bug we hit: only LOD0 got the controller, LOD1 kept the pack's `DemoAnimCont`, and since the in-game camera distance selects LOD1, it looked like nothing changed / "all animations at once.") The source clips are `Creep|Idle1_Action` / `Creep|Walk1_Action` from `Creep_mesh.fbx`, marked **loopTime=true** in the FBX import settings (they import non-looping by default). The rig is **Generic with a null Avatar** — that's normal for this pack and animates fine because the GameObject hierarchy matches the clip paths (don't "fix" the null avatar). ⚠️ **Walk-cycle vs slide mismatch:** the Walk clip is ~4.84s but a tile slide is only `TileMover.moveDuration` (0.25s), so only a sliver of the stride plays per move — if the walk reads as a twitch, either raise enemy `moveDuration` or bump the Walk state's **speed** in the controller. Attack/Death clips are deliberately unused: combat is a full-screen panel where the 3D model isn't shown, so those would only matter once models appear in the combat view. **New animations = add a state to `CreepAnimator` + a parameter, and set that parameter from a script** (extend `EnemyAnimator` or add a sibling) — keep gameplay decoupled from animation, same as `TileMover`.
- **Enemy is an abstract base + one subclass per behaviour** ([Enemy.cs](Assets/Scripts/Entities/Enemy.cs)). The base owns all shared state and helpers — `attackDamage`/`maxHealth`/health, `displayName`/`description` (shown in the hover tooltip), `CurrentTile`, `Init(...)`, `TakeDamage`, the visual clustering (`RelayoutTile`/`ClusterOffset`/`OnDestroy`), and the BFS helpers (`StepToward`, `MoveTo`, `EngagePlayer`). It exposes `protected` accessors `Graph`/`TurnManager`/`Player` and declares `public abstract void RunWorldTurn()`. Each concrete type is a tiny override:
  - **[Chaser.cs](Assets/Scripts/Entities/Chaser.cs)** — high dmg / low HP. Steps toward the player across the whole map and calls `EngagePlayer()` (→ `TurnManager.EnterCombat`) when its next step would land on the player. This is the original `Enemy` behaviour.
  - **[Brut.cs](Assets/Scripts/Entities/Brut.cs)** — low dmg / high HP. Same chase, but when the next step would be the player's tile it **returns without engaging** — stops one tile short and holds, occupying tiles around the player. It only fights if the player steps onto it (player-initiated combat via `Player.TryMoveTo`). "Block the best move toward the objective" is a deliberate later refinement, not implemented.
  - **[Protector.cs](Assets/Scripts/Entities/Protector.cs)** — low dmg / low HP. Ignores the player; patrols its home district's 3 streets in a fixed `0→1→2→0` loop (each hop is one edge since a district's streets are a fully-connected triangle). Reads `CurrentTile.Node.DistrictId` to find home and `Graph.GetStreet(home, i)` to advance. Never self-engages.
  - **New behaviours = new `Enemy` subclass** overriding `RunWorldTurn` + a prefab whose root carries that component. Stats (dmg/HP) live on the prefab, not in code. Don't re-add an `EnemyType` enum/switch — the polymorphic override IS the dispatch.
- **Enemy hover tooltip** ([Assets/Scripts/UI/EnemyInfoTooltip.cs](Assets/Scripts/UI/EnemyInfoTooltip.cs)). Each frame it raycasts from the mouse into the 3D scene (same resolver as [PlayerInputController.cs](Assets/Scripts/Player/PlayerInputController.cs) — enemy trigger colliders are hit because `queriesHitTriggers` defaults true) and, if an `Enemy` is under the cursor, shows a small card with `DisplayName` / `description` / `HP cur/max` / `ATK`. It re-populates every frame so HP stays live. Gated to `PlayerTurn`/`WorldTurn` only, so it never floats over the full-screen combat panel or end screens. **Same toggle-pattern caveat as CombatPanel:** the script lives on an always-active holder (`EnemyTooltip` under Canvas) and switches a CHILD `panelRoot` (`TooltipPanel`) on/off — never put it on the object it disables. The panel is an auto-sizing card (fixed 300px width + `VerticalLayoutGroup` + vertical `ContentSizeFitter`, top-left pivot) that follows the cursor with an offset and clamps to the screen (`rect.size × canvas.scaleFactor`). Identity strings live on the prefabs (per the `Enemy` subclass bullet), not in code.
- **Movement slides, logic stays instant** ([Assets/Scripts/Core/TileMover.cs](Assets/Scripts/Core/TileMover.cs)). `TileMover` is a tiny component on the Player and every Enemy that eases `transform.position` to a target over `moveDuration` (default 0.25s, SmoothStep). **It is visual only** — `CurrentTile`, clue collection, combat triggers and doom all resolve the instant the move happens; the slide just animates catching up. Both [Player.cs](Assets/Scripts/Player/Player.cs) and [Enemy.cs](Assets/Scripts/Entities/Enemy.cs) grab-or-add the mover in `Awake`, call `SnapTo(pos)` for spawn placement and `MoveTo(pos)` to glide. The Player gates `TryMoveTo` on `!_mover.IsMoving` so a click is ignored until the current slide finishes (one step at a time). Enemy world-turn slides play **one at a time**: `TurnManager.RunWorldTurn` waits on `enemy.IsMoving` before acting the next enemy. `Enemy.RelayoutTile` now routes the cluster fan-out through each occupant's mover too (snap on spawn, glide otherwise), so re-centring is smooth. A Chaser that engages does **not** move (it attacks from adjacent), so `IsMoving` is false and the combat wait runs immediately. **Facing:** `TileMover.FaceDirection(worldDir)` slerps the transform to look along a horizontal direction over `moveDuration` (with a `yawOffset` field for models whose forward isn't +Z — the creeps face +Z, so it's 0). `Enemy.MoveTo` calls it with the **node→node** direction (not the post-cluster position delta), so an enemy turns to face the tile it's actually walking to and cosmetic cluster re-fans don't spin survivors. The Player doesn't call it (its capsule has no meaningful facing); wire it in later when the detective gets a directional model.
- **Enemy stacking is visual-only**: multiple enemies may legitimately share a node. `Enemy.RelayoutTile(tile)` fans all occupants of a tile onto a small ring (`ClusterOffset`, radius 0.55) so the count is readable; it's called on spawn (`Place`), after each move (`RunWorldTurn`, re-laying both the vacated and entered tiles), and in `OnDestroy` (re-centre survivors). The graph/gameplay is unaffected — only `transform.position` changes.
- **Camera** ([Assets/Scripts/Core/CameraRig.cs](Assets/Scripts/Core/CameraRig.cs)) lives on the Main Camera. Edge-pan in screen space, project pan onto XZ via `Flatten(transform.right/forward)` so the direction is correct regardless of camera tilt. Bounds clamping operates on the **screen-center look-point** (raycast onto the y=0 plane), not the camera's own position — the camera body sits outside the grid, so clamping its position would lock it to the edge. Recenter computes the camera position needed to put the target at the look-point, then SmoothDamps to it.
- **Hotkeys use `UnityEngine.InputSystem.Key` fields on the consuming MonoBehaviour** (see [GameHUD.cs](Assets/Scripts/UI/GameHUD.cs) `endTurnKey`, [CameraRig.cs](Assets/Scripts/Core/CameraRig.cs) `recenterKey`) and read via `Keyboard.current[key].wasPressedThisFrame`. Gate the action with the same condition as the equivalent UI button (e.g. End Turn checks `CurrentState == PlayerTurn`). Don't add bindings to the `.inputactions` asset for one-off hotkeys.

All laid out via matched `anchorMin==anchorMax` anchors — keep that when editing (a mismatched `anchorMax` is what cramped an earlier pass).
- **`Main Camera`** — **orthographic** `CameraRig`. References: `Player`, `Graph`→Map. Pan bounds are computed from the min/max of all node positions in the graph. At Awake it applies `Euler(pitchDegrees, yawDegrees, 0)` for a corner-isometric look (pitch 30° = 2:1 dimetric, yaw 45° = viewed from a corner); disable `applyTiltOnAwake` to control rotation manually. `orthographicSize` is hand-tuned to frame the whole map (~9.25 at the current wide game-view aspect) — re-frame if the map bounds or aspect change.
- **`SceneNav`** (root GameObject) — has `SceneNav` ([Assets/Scripts/Core/SceneNav.cs](Assets/Scripts/Core/SceneNav.cs)). In SampleScene its `mainMenuButtons` array references the `MainMenuButton` child added to **both** `GameOverPanel` and `VictoryPanel` under Canvas; `SceneNav.Awake` subscribes each button's `onClick` to `LoadMainMenu()` at runtime (no inspector OnClick wiring). The end-game panels gain their "Main Menu" button this way. Note on tooling: wiring button `onClick` via `UnityEventTools.AddPersistentListener` from the Unity MCP `RunCommand` reliably crashes the bridge post-execution — so `SceneNav` wires listeners in `Awake` from serialized `Button` refs instead, and we set those refs via `SerializedObject`.
- **Prefabs in `Assets/Prefab/`** (note: folder is singular `Prefab/`, not `Prefabs/`): `TilePrefab`, `Player`, `CluePrefab` (Is Trigger), and the three enemy prefabs `Chaser` / `Brut` / `Protector`. The old single `EnemyPrefab` was removed when `Enemy` became abstract. **Enemy prefab structure (post-2026-06-04 model swap):** each enemy root keeps its `CapsuleCollider` (Is Trigger, height 2 — the click/hover-tooltip target), its `Enemy` subclass component, and `TileMover`. The **visual is now a child** — the **Creep Horror Creature** models (`Chaser`→`Creep1`, `Brut`→`Creep2`, `Protector`→`Creep3`, one texture set each from [Assets/Art/Enemies/](Assets/Art/Enemies/)), fitted to height ≈2 / centered / feet at local y=−1 (child localPos ≈ `(0, −0.86, −0.16)`, localScale ≈ `0.73`). The placeholder capsule `MeshFilter`/`MeshRenderer` were removed from the roots; the old colour-coded materials (crimson/brown/teal) are no longer used on the enemies. **The child model's `Animator` runs the shared `CreepAnimator` controller** (Idle⇄Walk, see the animation bullet below); each root also carries an `EnemyAnimator` component. ⚠️ All three share the same mesh (`Creep_mesh.fbx`) and their texture sets are visually similar (greyish-blue), so the enemy types are no longer instantly distinguishable by silhouette/colour — the hover tooltip carries the identity. The pack also ships `Creep_mesh_lod1.fbx` (low-detail LOD) if enemy counts ever grow.

- Enemy stats (per-prefab, baked into the `Chaser`/`Brut`/`Protector` prefabs): `Chaser` `attackDamage` = 2 / `maxHealth` = 1 (glass cannon); `Brut` = 1 / 4 (tanky blocker, never self-engages); `Protector` = 1 / 1 (passive patroller)

- `CombatController.attackKey` = `A`, `defendKey` = `D`
- `TileMover.moveDuration` — Player = 0.25s; the three enemy prefabs = **0.6s** (raised from 0.25 so the creep Walk cycle reads as an actual step rather than a twitch). 0 = instant teleport. World-turn enemy slides play sequentially, so total world-turn glide ≈ `moveDuration × enemyCount` (≈1.8s for the default 3 enemies). If that feels slow, drop enemy `moveDuration` or raise the Walk state speed in `CreepAnimator` instead.
